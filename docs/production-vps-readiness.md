Статус: чеклист перед первым production-релизом

## 1. Выбранная стартовая конфигурация

Провайдер: Timeweb Cloud.

| Ресурс |     Конфигурация | Оценка                                                                  |
| ------ | ---------------: | ----------------------------------------------------------------------- |
| ОС     | Ubuntu 26.04 LTS | Подходит для production и поддерживается Docker Engine                  |
| CPU    | 2 vCPU × 3,3 ГГц | Достаточно для MVP и небольшой одновременной нагрузки                   |
| RAM    |             4 ГБ | Минимально допустимый объём, требуется swap и мониторинг                |
| Диск   |       50 ГБ NVMe | Достаточно на старте, но медиа, backup и Docker images требуют контроля |
| Канал  |         1 Гбит/с | Достаточно с большим запасом; не является ожидаемым ограничением        |

На одном VPS запускаются `nginx`, `web` (Next.js), `cms` (Strapi),
`postgres`, `rustfs` и служебные контейнеры Certbot/RustFS init. Production
images собираются в GitHub Actions; сборка приложения на VPS запрещена.

## 2. Зафиксированные риски

| Риск                                                                                                | Вероятность / влияние | Меры                                                                                          |
| --------------------------------------------------------------------------------------------------- | --------------------- | --------------------------------------------------------------------------------------------- |
| Пик потребления RAM приводит к OOM и перезапуску Strapi, Next.js или PostgreSQL                     | Средняя / высокая     | Swap 4 ГБ, мониторинг RAM и OOM, готовность перейти на 8 ГБ                                   |
| Swap скрывает постоянный дефицит памяти и увеличивает задержки                                      | Средняя / средняя     | Считать swap только страховкой; масштабировать RAM при регулярном использовании swap          |
| Диск заполняется медиа, локальным backup, логами и старыми Docker images                            | Средняя / высокая     | Алерты, log rotation, контролируемая очистка неиспользуемых images, учёт размера backup       |
| Рабочие данные и локальные backup теряются вместе с VPS или диском                                  | Низкая / критическая  | Off-site backup PostgreSQL и RustFS и проверка восстановления                                 |
| Один VPS является единой точкой отказа                                                              | Средняя / высокая     | Риск принимается для MVP; документированное восстановление, мониторинг доступности            |
| Открытые наружу служебные порты раскрывают CMS, БД или object storage                               | Средняя / высокая     | Публиковать только 80/443; SSH ограничить; 1337/5432/9000 оставить в private Docker network   |
| Сертификат не продлевается автоматически                                                            | Низкая / высокая      | Systemd timer/cron для `tls-renew.sh`, проверка dry run и алерт по сроку сертификата          |
| Неограниченные Docker-логи исчерпывают диск                                                         | Средняя / высокая     | Настроить `json-file` rotation или другой ограниченный logging driver                         |
| Anonymous pull с Docker Hub блокируется общим rate limit IP провайдера                              | Наблюдалось / высокая | До первого deploy настроить registry authentication или проверенный источник публичных images |
| Неконтролируемое обновление ОС или контейнеров ломает production                                    | Низкая / высокая      | Фиксированные image tags/digests, security updates ОС, релизы только через protected tag      |
| Заявленные 3,3 ГГц и 1 Гбит/с не гарантируют постоянную производительность под совместной нагрузкой | Низкая / средняя      | Проверить реальную производительность smoke/load-тестом после развёртывания                   |

### 2.1. Уже подготовлено в репозитории

- Production Compose не наследует dev-зависимость `workspace-dependencies` и
  не требует исходников или сборочного toolchain на VPS.
- `web` и `cms` имеют readiness/healthchecks; Nginx запускается после их
  успешного прохождения.
- Для `web`, `cms`, `postgres`, `rustfs` и `nginx` задана ротация Docker-логов:
  `max-size=10m`, `max-file=3`.
- На VPS установлен Docker Engine `29.7.1` и Compose plugin `5.4.0`; пользователь
  `deploy` выполняет Docker-команды без `sudo`.
- `DOCKER-USER` вызывает versioned цепочку `BREGA-DOCKER-FIREWALL`: через
  публичный интерфейс разрешены только исходные TCP-порты `80/443`, остальные
  published ports блокируются. Systemd повторно применяет правила при рестарте
  Docker.
- Итоговый production Compose автоматически проверяется в CI: dev-зависимости,
  отсутствие build на VPS, healthcheck, log rotation и публикация только портов
  Nginx `80/443`.
- Первый deploy не запускает backup до появления application-контейнеров;
  последующие deploy сохраняют pre-deploy backup.
- Production images собираются в CI и задаются неизменяемыми ссылками; плавающий
  `latest` не используется.
- TLS bootstrap/renewal, локальный backup/restore, application rollback и
  smoke-check реализованы скриптами, но требуют rehearsal на настоящем VPS.

## 3. Обязательно до первого релиза

### 3.1. ОС и доступ

- [x] Создан отдельный непривилегированный пользователь `deploy`.
- [x] Вход по SSH разрешён только по ключу; вход `root` и парольная
      аутентификация отключены.
- [ ] Порт SSH ограничен доверенными IP, если операционный процесс это
      позволяет.
- [x] Установлены все security updates Ubuntu.
- [x] Настроена автоматическая установка security updates без автоматической
      перезагрузки.
- [x] Время синхронизируется через NTP; серверные логи и backup
      используют UTC.

### 3.2. Память

- [x] Создан swap-файл размером 4 ГБ с безопасными правами.
- [x] Проверено, что swap активируется после перезагрузки.
- [ ] Зафиксированы базовые значения RAM каждого контейнера после холодного
      старта и после типовых операций в Strapi Admin.
- [ ] Проверено отсутствие событий OOM в kernel journal.

Swap не считается дополнительной рабочей памятью. Он нужен только для того,
чтобы кратковременный пик не завершил критичный процесс.

### 3.3. Сеть и firewall

- [x] Из application-портов публично открыты только TCP `80` и `443`.
- [x] SSH открыт по согласованному правилу доступа.
- [x] UFW блокирует публичный доступ к портам `1337`, `5432` и `9000`.
- [x] Правила учитывают Docker `DOCKER-USER`; одного UFW без проверки
      фактической доступности портов недостаточно.
- [ ] После настройки выполнено внешнее сканирование публичных портов.

### 3.4. Docker

- [x] Docker Engine и Compose plugin установлены из официального Docker
      repository.
- [x] Для контейнеров настроена ротация логов, рекомендуемая стартовая политика:
      `max-size=10m`, `max-file=3`.
- [x] Production не содержит плавающих тегов `latest`.
- [x] Подтверждено конфигурацией и CI, что VPS только скачивает готовые images и не выполняет
      `yarn install`, Next.js build или Strapi build.
- [ ] Очистка неиспользуемых Docker images выполняется контролируемо и не
      удаляет текущий или rollback image.
- [ ] Настроен способ скачивания публичных images без anonymous Docker Hub rate
      limit; проверен pull всех production-зависимостей.

#### 3.4.1. Желательное улучшение: зеркало публичных images в GHCR

Статус: **отложено, в текущий deploy не входит**.

Если Docker Hub authentication окажется недостаточным или снова возникнут
ошибки rate limit, публичные production-зависимости можно зеркалировать в
GitHub Container Registry проекта. VPS в таком случае будет скачивать все
images из одного авторизованного registry.

- [ ] Зеркалировать только явно зафиксированные версии или digest, а не
      плавающие теги.
- [ ] Запускать синхронизацию вручную, в release pipeline или только при
      изменении списка внешних images; не выполнять её в каждом workflow/PR.
- [ ] Хранить текущую и предыдущую версии, необходимые для rollback.
- [ ] Настроить cleanup policy для удаления устаревших тегов без удаления
      текущих и rollback images.
- [ ] Перед переключением проверить pull всех зеркальных images с VPS и
      документировать возврат к исходному registry.

Ограничения GitHub, которые нужно учитывать при реализации:

- объём GHCR следует контролировать и очищать с учётом действующего тарифа;
- job зеркалирования на GitHub-hosted runner расходует Actions minutes; обычный
  pull с VPS Actions minutes не расходует;
- для снижения расхода storage и Actions minutes синхронизация должна запускаться
  только при выпуске новой закреплённой версии зависимости.

### 3.5. DNS и TLS

- [ ] `A`-записи storefront, admin и media направлены на публичный IP VPS.
- [ ] Если созданы `AAAA`-записи, IPv6 действительно настроен; иначе записи
      удалены.
- [ ] Порты 80/443 доступны для ACME challenge.
- [ ] Первый сертификат выпущен для всех трёх имён.
- [ ] `scripts/tls-renew.sh` запускается автоматически минимум раз в сутки.
- [ ] Выполнена тестовая попытка renewal, Nginx получает graceful reload.
- [ ] Настроен внешний контроль срока действия сертификата.

### 3.6. Данные и backup

- [ ] Persistent volumes PostgreSQL, RustFS и Let's Encrypt переживают
      пересоздание контейнеров.
- [ ] Ежедневный локальный backup хранит только последнюю копию.
- [ ] Pre-deploy backup выполняется до изменения production.
- [ ] Проведён тест восстановления PostgreSQL и RustFS из созданной копии.
- [ ] Согласовано место хранения off-site backup и срок хранения.
- [ ] Ключи off-site backup не дают публичного доступа к production media или
      базе данных.

Текущая архитектура MVP допускает только локальные backup на том же VPS, но
явно принимает риск полной потери данных при потере сервера. Для публичного
магазина off-site копия настоятельно рекомендуется до запуска.

### 3.7. Секреты и приложение

- [ ] Production `.env` находится вне Git и доступен только deploy-пользователю.
- [ ] Все секреты сгенерированы отдельно для production и не повторяют local/CI
      значения.
- [ ] PostgreSQL, Strapi, RustFS, email-провайдер, checkout и cache-revalidation используют
      разные секреты по назначению.
- [ ] Выполнены healthcheck и smoke-check storefront, admin, media и оформления
      заказа.
- [ ] Проверена отправка production email-уведомлений администратору и покупателю.

## 4. Мониторинг и пороги масштабирования

Минимально отслеживаются:

- доступность storefront и Strapi health endpoint;
- срок действия TLS-сертификата;
- RAM, swap, load average и события OOM;
- заполнение и I/O системного диска;
- состояние и количество рестартов контейнеров;
- HTTP 5xx и длительность ответа;
- успешность последнего backup.

Стартовые операционные пороги:

| Метрика   | Предупреждение                    | Действие                                                       |
| --------- | --------------------------------- | -------------------------------------------------------------- |
| RAM       | более 75% продолжительное время   | Проверить процессы и утечки                                    |
| RAM       | более 85% или регулярный swap I/O | Перейти на 8 ГБ RAM                                            |
| OOM       | любое событие                     | Разобрать немедленно; до устранения релиз считать нестабильным |
| Диск      | более 70%                         | Проверить media, backup, логи и images                         |
| Диск      | более 80%                         | Освободить место или увеличить диск до релиза                  |
| Диск      | более 90%                         | Критический инцидент, остановить некритичные записи/deploy     |
| Контейнер | неожиданный restart               | Проверить логи, OOM и healthcheck                              |
| TLS       | менее 21 дня до окончания         | Проверить renewal и исправить до истечения                     |

Переход на `2 vCPU / 8 ГБ RAM / 80–100 ГБ NVMe` выполняется, если наблюдается
хотя бы одно из условий:

- регулярное использование swap;
- RAM выше 85% в типовой нагрузке;
- OOM или повторные рестарты web/CMS/PostgreSQL;
- свободно менее 20% диска после штатной очистки;
- рост медиа и backup делает прогнозируемое заполнение диска ближе трёх
  месяцев;
- load-тест показывает неприемлемые задержки при ожидаемой одновременной
  нагрузке.

## 5. Проверка после развёртывания

- [ ] Перезагрузить VPS и убедиться, что Docker, контейнеры, swap и firewall
      восстановились автоматически.
- [ ] Проверить HTTPS и редирект HTTP → HTTPS для всех доменов.
- [ ] Проверить, что служебные порты недоступны извне.
- [ ] Создать тестовый заказ и проверить запись в Strapi и email.
- [ ] Загрузить изображение через Strapi, проверить выдачу через media-домен.
- [ ] Выполнить backup, удалить тестовые данные контролируемым способом и
      проверить восстановление в изолированной среде.
- [ ] Провести короткий load-тест согласованного пользовательского сценария и
      сохранить базовые показатели CPU, RAM и latency.
- [ ] Зафиксировать контакты ответственных и порядок действий при недоступности
      сайта, заполнении диска и неуспешном backup.

## 6. Итоговое решение

Конфигурация `2 vCPU / 4 ГБ RAM / 50 ГБ NVMe` принимается как стартовая для
MVP с небольшой нагрузкой. Она не имеет комфортного запаса по памяти и диску,
поэтому запуск разрешён только после настройки swap, log rotation, мониторинга,
backup и проверки восстановления. При небольшой разнице в стоимости
предпочтительна конфигурация с 8 ГБ RAM; масштабирование не требует изменения
архитектуры приложения.
