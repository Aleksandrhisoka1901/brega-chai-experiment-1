# ADR-002: Rendering и кэш Next.js

- Статус: принято
- Дата: 28 июля 2026

## Контекст

Большая часть storefront является публичным редакционным контентом, который
должен быстро загружаться и оставаться доступным при кратковременной
недоступности CMS. Корзина и checkout интерактивны, а создание заказа требует
актуальных серверных данных. Глобальный dynamic rendering увеличил бы задержку и
связал доступность каждой страницы с Strapi.

## Решение

Использовать Next.js App Router и Server Components по умолчанию. Client
Components ограничиваются интерактивными областями: навигацией, галереей,
счётчиком, корзиной и checkout.

Публичный контент работает cache-first с tag-based revalidation. Используются
смысловые теги `global`, `home`, `products`, `product:{documentId}` и
`product-slug:{type}:{slug}`. После publish, update или unpublish Strapi вызывает
защищённый идемпотентный `POST /api/revalidate`, который инвалидирует нужные
теги и страницы. Sitemap генерируется Strapi-плагином напрямую из актуальных
опубликованных документов и не использует Next.js cache.

Каталог и продуктовые страницы допускают stale-while-revalidate. Checkout и
создание заказа всегда работают с `no-store`. CMS доступна через server-only
client и mapper-слой; Strapi response и приватные credentials не пересекают
границу браузера.

## Последствия

- Закэшированные страницы продолжают работать при кратком сбое CMS.
- Первый незакэшированный запрос при недоступной CMS получает отдельный ответ
  service unavailable с `noindex`, а не ложный 404.
- Commerce endpoint не принимает заказ без актуальной серверной проверки.
- Webhook требует защиты секретом, allowlist событий, rate limit, безопасного
  сравнения и логирования без персональных данных.
- При горизонтальном масштабировании понадобится общий cache coordination;
  единственному web instance в MVP достаточно локального Next.js cache.
