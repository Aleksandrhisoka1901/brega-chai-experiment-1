# Исследование и рекомендация: интеграция службы доставки

- Статус: исследование (рекомендация; продуктовое решение и формальный ADR
  пока не приняты)
- Дата: 11 августа 2026 г.

## Контекст

Сейчас доставка полностью ручная (MVP, стадия `release-hardening`). В чекауте
два режима: *самовывоз* (адрес в Москве, скидка 10%) и *курьер* (стоимость
«рассчитывается в день отправки, до 1000 ₽», наличие и оплату подтверждает
менеджер). Онлайн-эквайринга нет, заказ создаётся как заявка.

Архитектура уже готовит почву под автоматизацию доставки:

- Next.js работает как BFF и граница доверия — браузер не обращается к API
  доставки/оплаты напрямую ([architecture-spec.md, разделы 11–13](architecture-spec.md)).
- Интеграция доставки вызывается только сервером, адрес хранится snapshot'ом
  ([architecture-spec.md, §13.2](architecture-spec.md#132-будущая-доставка)).
- Будущие delivery-адаптеры добавляются отдельным ADR и не утяжеляют текущий
  order-контракт.
- СДЭК уже поимённо упомянут как будущий delivery provider
  ([order-admin-spec.md, §10](order-admin-spec.md)).

Документ исследует двух кандидатов — **Яндекс Доставку** (B2B-продукт
«Доставка по России» / NDD) и **СДЭК** — и даёт рекомендацию по первому
адаптеру для чайного e-commerce с доставкой по РФ.

## Сравнение

| Критерий | **СДЭК** | **Яндекс (NDD «По России»)** |
|---|---|---|
| Чай как груз | разрешён (заводская упаковка, непортящийся) | **формально запрещён** в `limits.md` для тарифа «По России» — блокер, снимать с менеджера |
| Юр. статус | ИП / ООО / **самозанятый** | **только ИП / ООО** (NDD); самозанятый — только «Экспресс» |
| Договор / подключение | онлайн ~15 мин, бесплатно, без абонплаты; self-service | только через персонального менеджера + договор |
| Сеть | ~5 000 ПВЗ + ~3 300 постаматов, РФ + ЕАЭС | ~16 500 ПВЗ Яндекс Маркета, 2 000 городов |
| API | REST/JSON, API v2 (`api.cdek.ru/v2`) | REST/JSON; **два разных API** (other-day vs express — легко перепутать) |
| Авторизация | OAuth2 `client_credentials`, токен 3600 с | статичный Bearer (без refresh, инвалидируется при смене пароля ЛК) |
| Sandbox | `api.edu.cdek.ru/v2`, ключи в ЛК | `b2b.taxi.tst.yandex.net`, **публичный тестовый токен** (только Москва) |
| SDK | офиц. PHP + **типизированный Node/TS** (`shevernitskiy/cdek`), Python, Go, C# | SDK нет; есть офиц. Postman-коллекция NDD |
| Модуль под Next.js/Strapi | нет → самопис | нет → самопис |
| Вебхуки | полноценные (с 2025 — и на смену режима заказа) | push-поверх-поллинга; для other-day публично не описаны |
| Печать этикеток | `POST /v2/print/orders/{uuid}` | `request/generate-labels` + акты приёма-передачи |
| Забор курьером (intake) | `POST /v2/intake` | `pickups/create` (от 415 ₽/м³) или бесплатный самопривоз |
| Наложенный платёж | «Надёжная сделка» ~3% | `card_on_receipt`, `postpay` через GO/СМС |
| Тариф от | договорный «Посылка» от ~125 ₽ (до 3 кг) | от ~114 ₽ (размер S) |
| Вес (лимит) | «Посылка» до 50 кг | XL до 20 кг, негабарит до 30 кг |
| Главные риски | SPA-документация; внезапные breaking-changes; строгая валидация | запрет чая; разбросанная дока; нерегулярный changelog; недокументированные rate-limits |

## Что удобнее для доставки чая

СДЭК выигрывает по категории груза и операционке:

- чай проходит без юридических препятствий (заводская упаковка); у Яндекса та
  же категория стоит в явном запрете для нужного тарифа — правовой риск первого
  порядка;
- для лёгких посылок 50–500 г оптимален тариф «Посылка склад-ПВЗ / склад-дверь»
  (самые дешёвые варианты, большой выбор точек выдачи у получателя);
- наложенный платёж и страховка (~0,75%) покрывают сценарий «эквайринга пока
  нет».

Плюс Яндекса — бо́льшая собственная сеть ПВЗ (16 500) и сильная B2B-операционка
(примерка, бесплатное хранение, «Честный знак» 1.2, страхование до 250 000 ₽),
но всё это актуально только **после снятия запрета на чай**.

## Что проще интегрировать

Готового модуля ни под Next.js, ни под Strapi ни у кого нет — интеграция
самописная в обоих случаях. СДЭК проще по нескольким осям, которые ложатся на
текущую архитектуру:

- **Авторизация стандартнее**: классический OAuth2 `client_credentials` (токен
  кэшируется ~55 мин из 60) против статичного Bearer у Яндекса без refresh и с
  инвалидацией при смене пароля ЛК.
- **Готовый типизированный клиент** `shevernitskiy/cdek` (Node/TS, API v2):
  Zod-схемы ответов легко ложатся в `packages/contracts/`. У Яндекса SDK нет.
- **Вебхуки полноценные** (включая смену режима заказа); у Яндекса для other-day
  они публично не описаны — пришлось бы держать только cron-поллинг.
- **Один API** против двух независимых семейств эндпоинтов Яндекса
  (`/api/b2b/platform/*` для other-day vs `/b2b/cargo/integration/v2/*` для
  экспресса).

Плюс Яндекса для прототипирования: sandbox с опубликованным тестовым токеном и
складом — можно начать писать клиент без менеджера и договора (только адреса по
Москве). Это удобно для технического spike'а, но общего решения не меняет.

Как ложится на архитектуру:

- BFF-эндпоинты в Next.js: калькулятор стоимости + выбор ПВЗ + создание заявки;
- cron в Strapi: поллинг статусов (у Яндекса обязателен; у СДЭК — вебхук +
  поллинг как fallback);
- типизированный клиент + DTO/Zod — в `packages/contracts/` или новом
  `packages/delivery-cdek/`;
- токены — только в env, никогда в код;
- отдельный ADR на delivery-адаптер.

Оценка объёма самописной интеграции: ~5–15 дней в обоих случаях; у СДЭК — ближе
к нижней границе за счёт SDK.

## Условия и ограничения

| | **СДЭК** | **Яндекс (NDD)** |
|---|---|---|
| Форма бизнеса | ИП, ООО, самозанятый | только ИП / ООО |
| Договор | обязателен для полного API; онлайн, бесплатно | обязателен, через менеджера |
| Абонплата / мин. объём / плата за интеграцию | нет | публично не указано (pay-per-use) |
| Доступ к API без договора | только калькулятор | нет (токен из ЛК за менеджером) |
| Категории грузов | чай ок; запрещены скоропорт, контрафакт, опасные грузы | чай/продукты запрещены для «По России» |
| География | РФ + ЕАЭС; СДЭК Global — мир | РФ, 2 000 городов; ограничения по авиарегионам |

## Рекомендация

**Первым адаптером — СДЭК.** Три решающих фактора:

1. Чай у Яндекса формально запрещён тарифом «По России» (первоисточник —
   `limits.md` Яндекса) — это блокер, который до старта нужно снимать с
   менеджера письменно; у СДЭК категория разрешена.
2. Яндекс NDD доступен только ИП/юрлицу; СДЭК допускает все статусы, включая
   самозанятого.
3. Типизированный TS-SDK ложится прямо на стек; СДЭК уже заложен в спеку
   проекта как будущий provider.

Яндекс — жизнеспособен как **второй** адаптер (особенно «Экспресс» — курьер по
Москве день-в-день), но только после решения вопроса с чаем в письменном виде и
при наличии ИП.

## Риски и открытые вопросы

Для СДЭК (минимальный набор):

- заключить договор как **ИП** (рекомендуется) — договорной тариф «Посылка» от
  ~125 ₽ и наложенный платёж;
- запросить у менеджера **договорные тарифы** под объём/направления (публичный
  калькулятор дороже на 30–55%);
- уточнить формат тестового доступа (`Account` + `Secure password` в ЛК →
  `api.edu.cdek.ru`);
- заложить бюджет на сопровождение: СДЭК периодически меняет API (breaking-change
  01.03.2024 ломал рабочие интеграции), нужна подписка на changelog и ретраи.

Для Яндекса (только после пунктов ниже):

- **письменное подтверждение менеджера**, что чай для B2B-юрлица по тарифу «По
  России» отправлять можно (формальный запрет в `limits.md` — главный риск
  проекта) и при каких условиях;
- наличие/включение вебхуков для other-day + rate-limits + процедура перехода
  sandbox → prod;
- оформленный ИП (для NDD самозанятости недостаточно).

## Следующие шаги

1. Зафиксировать решение в **ADR-005** (по шаблону
   [ADR-003](adr/ADR-003-order-stock-and-cart.md)).
2. На стороне бизнеса — заключить договор с СДЭК как ИП, получить договорной
   тариф и API-ключи.
3. Технически начать с `shevernitskiy/cdek` + официальной документации
   [apidoc.cdek.ru](https://apidoc.cdek.ru/); первым эндпоинтом в BFF —
   калькулятор `/v2/calculator/tarifflist`, чтобы показывать стоимость доставки
   на витрине вместо текущего «рассчитывается в день отправки».
