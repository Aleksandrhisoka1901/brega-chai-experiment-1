# Brega Chai — спецификация управления заказами в Strapi Admin

Статус: реализовано.
Контекст: Commerce MVP и state machine заказа уже реализованы; эта
спецификация меняет только административный интерфейс и не переносит
commerce-домен в сторонний плагин.

## 1. Цель

Дать менеджеру отдельное рабочее место для обработки заказов без редактирования
сырого JSON и технических полей Content Manager.

Интерфейс должен:

- быстро показывать новые заказы и их текущее состояние;
- представлять покупателя, доставку, позиции и сумму в читаемом виде;
- позволять менеджеру корректировать адрес, состав заказа и внутренний
  комментарий с транзакционным пересчётом суммы и остатков;
- разрешать только допустимые переходы статуса;
- сохранять существующую транзакционную логику stock и историю статусов;
- не раскрывать технические ключи и лишние персональные данные.

## 2. Архитектурное решение

Реализовать внутренний Strapi 5 plugin `order-admin` с отдельным пунктом
«Заказы» в основном меню Admin.

Плагин состоит из:

- admin React-приложения на Strapi Design System;
- admin-only server routes;
- mapper из внутренней order-модели в явные list/detail DTO;
- вызова существующих commerce-сервисов для редактирования заказа и смены
  статуса.

Стандартный Content Manager не является рабочим интерфейсом менеджера для
заказов. Доступ к нему можно оставить только Super Admin как технический
fallback; создание и удаление заказа через Admin запрещены.

## 3. Роли и доступ

Плагин регистрирует отдельные RBAC actions:

- `plugin::order-admin.read` — список и карточка заказа;
- `plugin::order-admin.transition` — изменение статуса;
- `plugin::order-admin.edit` — изменение адреса, состава и комментария
  менеджера.

Правила:

- без `read` пункт меню и routes недоступны;
- `transition` и `edit` не подразумеваются из `read` и назначаются независимо;
- Content API и Public role не получают доступ к заказам;
- server routes возвращают только явные DTO, а не сырую Strapi entity;
- ошибки и логи не содержат телефон, email, адрес, комментарий или согласия.

## 4. Список заказов

### 4.1. Состав

Таблица показывает:

- номер заказа;
- дату и время создания;
- имя покупателя;
- статус;
- количество товарных позиций;
- общее количество единиц;
- сумму в рублях.

Заказы по умолчанию сортируются от новых к старым. Клик по строке или номеру
открывает карточку заказа.

### 4.2. Поиск и фильтры

MVP поддерживает:

- поиск по точному или частичному номеру заказа;
- поиск по имени покупателя;
- фильтр по статусу;
- диапазон даты создания;
- серверную пагинацию.

Телефон, email и адрес не используются как list columns. Поиск по ним не входит
в первый срез, чтобы не размножать PII в URL, логах и таблице.

### 4.3. Состояния

Предусмотреть:

- loading skeleton;
- пустой список;
- отсутствие результатов фильтра;
- безопасную ошибку загрузки с повтором;
- disabled/pending состояние перехода на карточку.

## 5. Карточка заказа

### 5.1. Шапка

Шапка содержит:

- `Заказ {orderNumber}`;
- дату и время создания;
- badge текущего статуса;
- сумму;
- доступные действия перехода статуса.

Русские подписи:

- `new` — «Новый»;
- `confirmed` — «Подтверждён»;
- `completed` — «Выполнен»;
- `cancelled` — «Отменён».

### 5.2. Покупатель и доставка

Отдельные читаемые блоки:

- имя;
- телефон со ссылкой `tel:`;
- email со ссылкой `mailto:`, если заполнен;
- адрес доставки;
- комментарий или явное пустое состояние.

Значения доступны для копирования. Имя, телефон, email и комментарий покупателя
остаются immutable snapshot и через Admin не исправляются. Для заказов в
статусах `new` и `confirmed` менеджер с правом `edit` может изменить адрес
получения и отдельный внутренний `managerComment`, который покупателю не
показывается.

### 5.3. Состав заказа

Вместо JSON отображается таблица:

- название товара;
- фасовка;
- цена за единицу;
- количество;
- сумма позиции.

При чтении карточка использует сохранённый order snapshot и не пересчитывает его
по актуальному каталогу. При явном редактировании менеджер может изменить
количество, удалить позицию или добавить опубликованный товар в наличии:

- существующая позиция сохраняет цену из order snapshot;
- новая позиция получает текущие отображаемое название, фасовку и цену товара;
- количество ограничено диапазоном `1–5` и доступным остатком;
- в заказе должна остаться минимум одна позиция;
- стандартная сумма и сумма со скидкой пересчитываются сервером;
- разница в остатках резервируется или возвращается в одной транзакции.

Ручной ввод цены и суммы не поддерживается. Форматирование выполняется через
`Intl.NumberFormat("ru-RU")`.

### 5.4. История

Timeline показывает:

- создание заказа;
- каждый переход статуса;
- дату и время события;
- предыдущий и новый статус.
- пользователя, выполнившего переход; для автоматических и старых событий без
  actor snapshot выводится «Система».

`statusHistory` отображается read-only. Сырой JSON не показывается.

Согласия отображаются компактным read-only блоком: тип согласия, факт принятия
и версия документа. Технические `idempotencyKey`, `requestFingerprint`,
внутренние record IDs и `stockRecordId` в UI отсутствуют.

## 6. Переходы статуса

UI строит действия из того же контракта, что domain policy:

```text
new ─► confirmed ─► completed
 │         │
 └─────────┴────────────► cancelled
```

Требования:

- текущий статус нельзя выбрать повторно;
- недопустимые переходы не отображаются и отклоняются сервером;
- переход выполняется только через `transitionStatus`;
- во время запроса действия блокируются и показывают spinner;
- успешный переход обновляет badge, действия и timeline без полной перезагрузки;
- ошибка оставляет прежнее состояние и показывает безопасное сообщение;
- каждый переход требует confirm dialog; отмена дополнительно поясняет возврат
  товарных остатков;
- повторная или конкурентная команда безопасно отклоняется после повторного
  чтения актуального статуса.
- подтверждение заказа повторно проверяет существование каждого товара по
  стабильному `documentId`; если товар удалён, статус не меняется, а менеджер
  видит название проблемной позиции и понятное требование исправить заказ;
- отмена возвращает остаток по стабильному `documentId` в актуальные строки
  товара, не полагаясь на физический record ID published-версии;
- полностью удалённый товар не блокирует отмену: возврат для этой позиции
  пропускается, остальные позиции и статус обрабатываются в одной транзакции.
- после успешного редактирования состава заказа и после отмены CMS синхронно
  запрашивает подписанную ревалидацию товарных кешей витрины; подтверждение и
  завершение заказа ревалидацию stock не вызывают, поскольку остаток не меняют;
- ошибка доставки ревалидации не откатывает уже завершённую stock-транзакцию и
  не превращает успешную административную операцию в ложную ошибку.

Числовой `stockRecordId` в старых snapshot допускается только для обратной
совместимости и диагностики. Commerce-операции не используют его как связь с
товаром, поскольку Strapi может заменить physical row при повторной публикации.

## 7. Admin API

Плановый контракт:

```text
GET  /order-admin/orders
GET  /order-admin/products
GET  /order-admin/orders/:documentId
PUT  /order-admin/orders/:documentId
POST /order-admin/orders/:documentId/status
```

List query:

```text
page, pageSize, search, status, createdFrom, createdTo
```

Status body:

```json
{ "status": "confirmed" }
```

Edit body содержит optimistic-lock значение `expectedUpdatedAt`, новый адрес,
необязательный комментарий менеджера и массив `{ productId, quantity }`. Цены и
итоги клиент не передаёт.

Routes имеют тип `admin`, используют Strapi admin authentication/RBAC и строгую
валидацию query, params и body. `PUT` и `POST` возвращают обновлённый detail DTO.

API не предоставляет create, arbitrary update или delete. Узкий `PUT` допускает
только описанное редактирование заказов в статусах `new` и `confirmed`, проверяет
версию заказа и возвращает обновлённый detail DTO.

## 8. Доступность и UX

- все действия доступны с клавиатуры;
- таблица использует семантические заголовки;
- badge не является единственным носителем статуса — рядом есть текст;
- focus после confirm dialog возвращается на trigger;
- после успешного перехода статус объявляется через polite live region;
- ошибки связаны с действием и не создают layout shift;
- loading и disabled состояния различимы без опоры только на цвет;
- edit dialog доступен с клавиатуры, показывает пересчитанный итог до сохранения
  и не закрывается во время запроса;
- интерфейс использует русскую локаль и компоненты Strapi Design System.

## 9. Наблюдаемость

Логируются только:

- тип операции: переход статуса или редактирование;
- `documentId` заказа;
- исходный и целевой статус для перехода;
- идентификатор администратора;
- результат и технический error code.

PII и содержимое заказа в application logs не записываются. Каждый
пользовательский переход сохраняет в `statusHistory` минимальный actor snapshot:
стабильный ID администратора и отображаемое имя. Это сохраняет читаемость
истории после переименования или удаления пользователя без копирования полного
профиля.

## 10. Не входит в MVP

- создание заказа менеджером;
- редактирование имени, телефона, email и комментария покупателя;
- ручное изменение unit price, скидки или итоговой суммы независимо от состава;
- удаление и архивирование заказов;
- платежи, возвраты денег и фискализация;
- СДЭК и другие delivery providers;
- Telegram-уведомления и повторная отправка уведомлений из order-admin;
- массовая смена статусов;
- экспорт, печать и аналитический dashboard;
- миграция заказов в Medusa, Shopify или иной commerce backend.

## 11. Acceptance criteria

1. Менеджер с `read` видит список и карточку, но без `transition` не меняет
   статус, а без `edit` не видит действие редактирования.
2. Список имеет серверные поиск, status/date filters, сортировку и пагинацию.
3. Карточка не показывает сырой JSON и технические ключи.
4. При чтении позиции и сумма берутся из snapshot заказа; редактирование меняет
   только адрес, состав и комментарий менеджера через отдельную команду.
5. Все переходы проходят через `transitionStatus`; недопустимый переход не
   изменяет заказ или stock.
6. Отмена один раз возвращает stock и требует подтверждения в UI.
7. После перехода badge и timeline обновляются без reload.
8. Добавление, удаление и изменение количества позиций атомарно корректирует
   stock и пересчитывает обе суммы; при ошибке заказ и остатки не меняются.
9. Одновременное редактирование защищено `expectedUpdatedAt`; завершённые и
   отменённые заказы недоступны для редактирования.
10. После изменения stock свежая загрузка витрины получает новое значение без
    ожидания TTL; открытая карточка товара обновляет live-остаток при возврате
    фокуса и не позволяет увеличить выбранное количество выше него.
11. API не позволяет создать, удалить или произвольно обновить заказ.
12. Unit, integration и admin UI tests покрывают DTO, RBAC, list/detail,
    редактирование, переходы, ошибки и keyboard flow.
13. CMS typecheck, build и существующая commerce suite остаются зелёными.

## 12. Результат реализации

Внутренний plugin `order-admin` реализован без изменения commerce-модели:

- list/detail DTO валидируются и исключают технические поля;
- admin-only API защищён отдельными `read`, `transition` и `edit` actions;
- список поддерживает серверные поиск, status/date filters и пагинацию;
- карточка показывает server-owned snapshot заказа, контакты, доставку, согласия и
  timeline;
- edit dialog меняет адрес, состав и комментарий менеджера, автоматически
  пересчитывает суммы и транзакционно корректирует stock;
- существующие позиции сохраняют snapshot-цену, новые получают текущую цену;
- действия строятся из разрешённых переходов и вызывают только
  `transitionStatus`;
- отмена требует подтверждения, а pending/error/success состояния не допускают
  повторной команды;
- статус объявляется assistive technologies, dialog возвращает focus, а
  телефон и email доступны как нативные ссылки;
- audit log содержит только тип операции, `documentId`, статусы перехода,
  administrator ID, результат и технический error code.

Проверки реализации: CMS unit suite, отдельный admin TypeScript project,
production Strapi Admin build и live authenticated list/detail/edit smoke.
