# Brega Chai — спецификация управления заказами в Strapi Admin

Статус: реализовано.
Контекст: Commerce MVP и state machine заказа уже реализованы; эта
спецификация меняет только административный интерфейс и не переносит
commerce-домен в сторонний плагин.

## 1. Цель

Дать менеджеру отдельное рабочее место для обработки заказов без редактирования
сырого JSON и технических полей Content Manager.

Интерфейс должен:

- быстро показывать новые заказы и их текущее состояние;
- представлять покупателя, доставку, позиции и сумму в читаемом виде;
- разрешать только допустимые переходы статуса;
- сохранять существующую транзакционную логику stock и историю статусов;
- не раскрывать технические ключи и лишние персональные данные.

## 2. Архитектурное решение

Реализовать внутренний Strapi 5 plugin `order-admin` с отдельным пунктом
«Заказы» в основном меню Admin.

Плагин состоит из:

- admin React-приложения на Strapi Design System;
- admin-only server routes;
- mapper из внутренней order-модели в явные list/detail DTO;
- вызова существующего `api::order.order.transitionStatus` для смены статуса.

Стандартный Content Manager не является рабочим интерфейсом менеджера для
заказов. Доступ к нему можно оставить только Super Admin как технический
fallback; создание и удаление заказа через Admin запрещены.

## 3. Роли и доступ

Плагин регистрирует отдельные RBAC actions:

- `plugin::order-admin.read` — список и карточка заказа;
- `plugin::order-admin.transition` — изменение статуса.

Правила:

- без `read` пункт меню и routes недоступны;
- `transition` не подразумевается из `read`;
- Content API и Public role не получают доступ к заказам;
- server routes возвращают только явные DTO, а не сырую Strapi entity;
- ошибки и логи не содержат телефон, email, адрес, комментарий или согласия.

## 4. Список заказов

### 4.1. Состав

Таблица показывает:

- номер заказа;
- дату и время создания;
- имя покупателя;
- статус;
- количество товарных позиций;
- общее количество единиц;
- сумму в рублях.

Заказы по умолчанию сортируются от новых к старым. Клик по строке или номеру
открывает карточку заказа.

### 4.2. Поиск и фильтры

MVP поддерживает:

- поиск по точному или частичному номеру заказа;
- поиск по имени покупателя;
- фильтр по статусу;
- диапазон даты создания;
- серверную пагинацию.

Телефон, email и адрес не используются как list columns. Поиск по ним не входит
в первый срез, чтобы не размножать PII в URL, логах и таблице.

### 4.3. Состояния

Предусмотреть:

- loading skeleton;
- пустой список;
- отсутствие результатов фильтра;
- безопасную ошибку загрузки с повтором;
- disabled/pending состояние перехода на карточку.

## 5. Карточка заказа

### 5.1. Шапка

Шапка содержит:

- `Заказ {orderNumber}`;
- дату и время создания;
- badge текущего статуса;
- сумму;
- доступные действия перехода статуса.

Русские подписи:

- `new` — «Новый»;
- `confirmed` — «Подтверждён»;
- `completed` — «Выполнен»;
- `cancelled` — «Отменён».

### 5.2. Покупатель и доставка

Отдельные читаемые блоки:

- имя;
- телефон со ссылкой `tel:`;
- email со ссылкой `mailto:`, если заполнен;
- адрес доставки;
- комментарий или явное пустое состояние.

Значения доступны для копирования. В MVP это immutable snapshot: исправление
контактных данных через Admin не поддерживается.

### 5.3. Состав заказа

Вместо JSON отображается таблица:

- название товара;
- фасовка;
- цена за единицу;
- количество;
- сумма позиции.

Ни одна цена не запрашивается повторно из текущего товара: карточка использует
сохранённый order snapshot. Итог сверяется с `totalRubles`, форматирование
выполняется через `Intl.NumberFormat("ru-RU")`.

### 5.4. История

Timeline показывает:

- создание заказа;
- каждый переход статуса;
- дату и время события;
- предыдущий и новый статус.
- пользователя, выполнившего переход; для автоматических и старых событий без
  actor snapshot выводится «Система».

`statusHistory` отображается read-only. Сырой JSON не показывается.

Согласия отображаются компактным read-only блоком: тип согласия, факт принятия
и версия документа. Технические `idempotencyKey`, `requestFingerprint`,
внутренние record IDs и `stockRecordId` в UI отсутствуют.

## 6. Переходы статуса

UI строит действия из того же контракта, что domain policy:

```text
new ─► confirmed ─► completed
 │         │
 └─────────┴────────────► cancelled
```

Требования:

- текущий статус нельзя выбрать повторно;
- недопустимые переходы не отображаются и отклоняются сервером;
- переход выполняется только через `transitionStatus`;
- во время запроса действия блокируются и показывают spinner;
- успешный переход обновляет badge, действия и timeline без полной перезагрузки;
- ошибка оставляет прежнее состояние и показывает безопасное сообщение;
- каждый переход требует confirm dialog; отмена дополнительно поясняет возврат
  товарных остатков;
- повторная или конкурентная команда безопасно отклоняется после повторного
  чтения актуального статуса.

## 7. Admin API

Плановый контракт:

```text
GET  /order-admin/orders
GET  /order-admin/orders/:documentId
POST /order-admin/orders/:documentId/status
```

List query:

```text
page, pageSize, search, status, createdFrom, createdTo
```

Status body:

```json
{ "status": "confirmed" }
```

Routes имеют тип `admin`, используют Strapi admin authentication/RBAC и строгую
валидацию query, params и body. `POST` возвращает обновлённый detail DTO.

API не предоставляет create, arbitrary update или delete.

## 8. Доступность и UX

- все действия доступны с клавиатуры;
- таблица использует семантические заголовки;
- badge не является единственным носителем статуса — рядом есть текст;
- focus после confirm dialog возвращается на trigger;
- после успешного перехода статус объявляется через polite live region;
- ошибки связаны с действием и не создают layout shift;
- loading и disabled состояния различимы без опоры только на цвет;
- интерфейс использует русскую локаль и компоненты Strapi Design System.

## 9. Наблюдаемость

Логируются только:

- `documentId` заказа;
- исходный и целевой статус;
- идентификатор администратора;
- результат и технический error code.

PII и содержимое заказа в application logs не записываются. Каждый
пользовательский переход сохраняет в `statusHistory` минимальный actor snapshot:
стабильный ID администратора и отображаемое имя. Это сохраняет читаемость
истории после переименования или удаления пользователя без копирования полного
профиля.

## 10. Не входит в MVP

- создание заказа менеджером;
- редактирование покупателя, адреса, состава, цен и суммы;
- удаление и архивирование заказов;
- платежи, возвраты денег и фискализация;
- СДЭК и другие delivery providers;
- email/Telegram-уведомления;
- массовая смена статусов;
- экспорт, печать и аналитический dashboard;
- миграция заказов в Medusa, Shopify или иной commerce backend.

## 11. Acceptance criteria

1. Менеджер с `read` видит список и карточку, но без `transition` не меняет
   статус.
2. Список имеет серверные поиск, status/date filters, сортировку и пагинацию.
3. Карточка не показывает сырой JSON и технические ключи.
4. Позиции и сумма берутся из immutable snapshot заказа.
5. Все переходы проходят через `transitionStatus`; недопустимый переход не
   изменяет заказ или stock.
6. Отмена один раз возвращает stock и требует подтверждения в UI.
7. После перехода badge и timeline обновляются без reload.
8. API не позволяет создать, удалить или произвольно обновить заказ.
9. Unit, integration и admin UI tests покрывают DTO, RBAC, list/detail,
   переходы, ошибки и keyboard flow.
10. CMS typecheck, build и существующая commerce suite остаются зелёными.

## 12. Результат реализации

Внутренний plugin `order-admin` реализован без изменения commerce-модели:

- list/detail DTO валидируются и исключают технические поля;
- admin-only API защищён отдельными `read` и `transition` actions;
- список поддерживает серверные поиск, status/date filters и пагинацию;
- карточка показывает immutable snapshot заказа, контакты, доставку, согласия и
  timeline;
- действия строятся из разрешённых переходов и вызывают только
  `transitionStatus`;
- отмена требует подтверждения, а pending/error/success состояния не допускают
  повторной команды;
- статус объявляется assistive technologies, dialog возвращает focus, а
  телефон и email доступны как нативные ссылки;
- audit log содержит только `documentId`, статусы, administrator ID, результат
  и технический error code.

Проверки реализации: CMS unit suite, отдельный admin TypeScript project,
production Strapi Admin build и live authenticated list/detail smoke.
