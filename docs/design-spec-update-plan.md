# План обновления дизайн-спецификации Brega Chai

Статус: запланировано

Основной документ: [design-spec.md](./design-spec.md)

HTML-референс: [design-reference.html](./design-reference.html)
Дата: 27 июля 2026

## Цель

Превратить текущую дизайн-спеку из описания визуального направления в исполнимый контракт для дизайна, разработки, наполнения CMS и приёмки интерфейса.

После обновления разработчику не потребуется самостоятельно определять состояния компонентов, допустимые цветовые пары, поведение форм, системную обратную связь и критерии качества.

## 1. Формализовать цветовую систему

Добавить раздел `Color Pairings`:

- разрешённые сочетания текста и фона;
- рассчитанный контраст каждой пары;
- цвета hover, active, focus и disabled;
- варианты CTA на светлом, sage и тёмном фоне;
- правила CMS при выборе секционного цвета;
- запрещённые сочетания.

Результат: готовая таблица цветов, которую можно напрямую перенести в design tokens и тесты контраста.

## 2. Дополнить систему токенов

Расширить раздел `Design tokens`:

- fluid typography;
- line-height и letter-spacing;
- максимальные ширины контейнеров;
- breakpoints;
- размеры controls и иконок;
- aspect ratios изображений;
- z-index;
- focus ring;
- disabled-состояния;
- safe-area;
- drawer elevation;
- skeleton colors;
- motion properties.

Результат: практически готовый CSS-контракт.

## 3. Описать состояния компонентов

Добавить `Component States` для:

- кнопок;
- ссылок;
- карточек;
- счётчика количества;
- полей;
- checkbox;
- выбора города и ПВЗ;
- галереи;
- карусели;
- корзины.

Для каждого зафиксировать:

- default;
- hover;
- focus-visible;
- active/pressed;
- disabled;
- loading;
- error;
- empty.

Результат: все интерактивные состояния определены до реализации.

## 4. Формализовать системную обратную связь

Добавить раздел `System Feedback`:

- inline validation;
- form error summary;
- alert;
- toast/live region;
- skeleton;
- progress;
- empty state;
- success;
- service unavailable;
- offline/timeout;
- 404/500;
- изменение цены;
- товар снят с продажи.

Результат: единый визуальный язык штатных, переходных и ошибочных состояний.

## 5. Уточнить формы и checkout

Расширить требования к формам:

- `label`, `name`, `type` и `inputmode`;
- `autocomplete`;
- разрешённый paste;
- обязательные поля;
- загрузка и повторная отправка;
- фокус на первой ошибке;
- сохранение введённых данных;
- предупреждение при закрытии незавершённого checkout;
- поведение клавиатуры на мобильных устройствах;
- единая зона нажатия checkbox и его label.

Результат: проверяемая спецификация checkout-интерфейса.

## 6. Описать карусель и интерактивные панели

Для «Ритуалов», товарной галереи и корзины определить:

- keyboard navigation;
- focus management;
- доступные названия controls;
- объявление изменений;
- scroll snap;
- touch gestures;
- overscroll;
- interruptible motion;
- reduced motion;
- блокировку фоновой прокрутки;
- safe-area.

Результат: точный контракт интерактивного поведения.

## 7. Добавить техническую media-матрицу

Зафиксировать требования для каждого типа изображения:

| Слот | Aspect ratio | Минимальный размер | Crop | Загрузка |
| --- | --- | --- | --- | --- |
| Hero desktop | определить | определить | focal point | priority |
| Hero mobile | определить | определить | отдельный crop | priority |
| Карточка | `4:5` или `3:4` | определить | единый масштаб | lazy |
| Галерея товара | определить | определить | contain/cover | mixed |
| Rich content | свободнее | определить | editorial | lazy |
| OG image | `1.91:1` | 1200×630 | safe area | server |

Дополнительно определить:

- допустимые форматы;
- максимальный вес;
- правила прозрачного фона;
- обязательность `width` и `height`;
- alt;
- placeholder;
- поведение отсутствующего изображения.

Результат: изображения можно готовить и валидировать до загрузки в CMS.

## 8. Дополнить типографику и локализацию

Добавить правила:

- `text-wrap: balance/pretty`;
- русские кавычки;
- многоточие;
- неразрывные пробелы;
- цены и единицы измерения;
- `Intl.NumberFormat`;
- даты;
- tabular numerals;
- длинные слова и URL;
- минимальные и максимальные тексты;
- rich-content hierarchy.

Результат: стабильная вёрстка на реальном русскоязычном контенте.

## 9. Расширить accessibility-раздел

Зафиксировать:

- skip link;
- heading hierarchy;
- landmarks;
- `scroll-margin-top` для якорей;
- focus order;
- focus trapping;
- live regions;
- zoom 200%;
- reflow;
- keyboard-only flow;
- отсутствие hover-only действий;
- декоративные элементы в accessibility tree.

Результат: требования можно проверять в E2E и ручном аудите.

## 10. Описать rich content

Добавить правила отображения:

- `h2–h4`;
- абзацев;
- списков;
- цитат;
- ссылок;
- изображений и подписей;
- пошаговых инструкций;
- характеристик;
- таблиц;
- горизонтальных разделителей;
- пустых блоков;
- широких media-вставок.

Результат: статьи товаров не разрушают общий визуальный язык.

## 11. Добавить измеримый Design QA

Создать финальный acceptance checklist:

- viewport 320, 390, 768, 1024, 1440 и 1920 px;
- Chrome, Safari, Firefox и Edge;
- отсутствие горизонтального скролла;
- zoom 200%;
- keyboard-only;
- contrast audit;
- reduced motion;
- screen-reader smoke test;
- минимальный и максимальный контент;
- missing image;
- visual regression;
- image/font budgets;
- Core Web Vitals.

Результат: дизайн принимается по воспроизводимым критериям, а не по общему впечатлению.

## 12. Синхронизировать HTML-референс

После обновления документа:

- применить новые tokens;
- добавить focus, active и disabled;
- показать системные состояния;
- проверить mobile safe-area;
- исправить доступность карусели;
- добавить примеры форм и drawer либо вынести их в отдельный component showcase;
- сверить HTML со спекой.

Результат: HTML-референс остаётся наглядным выражением актуальной спецификации.

## Порядок выполнения

1. Цвета и tokens.
2. Типографика и media matrix.
3. Component states.
4. Forms и system feedback.
5. Интерактивность и accessibility.
6. Rich content.
7. Design QA.
8. Обновление HTML-референса.
9. Перекрёстная проверка product, architecture и design specs.

## Критерии завершения

План считается выполненным, когда:

- все новые разделы добавлены в `design-spec.md`;
- правила не противоречат продуктовой и архитектурной спекам;
- ключевые значения представлены токенами или таблицами;
- для каждого интерактивного компонента описаны состояния;
- системные и ошибочные состояния имеют визуальные правила;
- accessibility-требования измеримы;
- media-матрица пригодна для подготовки контента;
- HTML-референс синхронизирован с документом;
- финальный Design QA checklist можно использовать при приёмке.
