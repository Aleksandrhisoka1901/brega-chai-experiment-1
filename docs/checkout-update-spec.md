# Brega Tea — спецификация доработки checkout и уведомлений

Статус: реализовано. Production-проверка email-провайдера и реальных адресов
получателей входит в release-readiness.

Основание: `ТЗ_сайт_2.docx` и решения grill-me от 31 июля 2026 года.

Эта спецификация уточняет и заменяет требования разделов 6.10
`product-spec.md`, 12.2–12.3 `architecture-spec.md` и исключение email-уведомлений
из `order-admin-spec.md` в части, где они противоречат этому документу.

## 1. Публичный бренд

- Публичное название проекта — `Brega Tea`.
- Видимые тексты, SEO, structured data, seed и письма используют новое имя.
- Технические идентификаторы `brega-chai`, имена пакетов, ключи хранилища и
  Docker-сервисов не переименовываются.
- Пока поле `logo` в общих настройках пустое, header и footer показывают
  текстовый логотип `Brega Tea` локальным Cormorant Garamond.
- Поле `logo` остаётся необязательным для будущего графического логотипа;
  текущее seed-значение очищается.

## 2. Управляемые настройки CMS

В опубликованных общих настройках обязательны:

- `pickupAddress` — адрес и график самовывоза; начальное значение:
  `г. Москва, ул. Чайная, д. 1. Ежедневно с 10:00 до 22:00.`;
- `pickupDiscountPercent` — целое число от 0 до 100; начальное значение `10`;
- `courierDeliveryNote` — начальное значение:
  `Стоимость рассчитывается в день отправки, до 1000 руб.`;
- `maxItemQuantity` — максимальное количество одного товара или набора в
  корзине и заказе, целое число от 1 до 100; начальное значение `5`;
- `orderNotificationEmail` — отдельный служебный email получателя заказов,
  который не публикуется на витрине.

## 3. Checkout

Checkout остаётся вторым состоянием текущей выезжающей корзины.
Перед переключением drawer в checkout storefront запрашивает актуальные остатки
всех позиций через `no-store` BFF endpoint. Если остаток уменьшился, drawer
остаётся в состоянии корзины, обновляет quantity controls и показывает
сообщение. После успешного заказа серверный product cache инвалидируется, а
текущая вкладка фоново обновляет stock store без навигации или визуальной
перезагрузки страницы.

### Шаг 1. Способ получения

- По умолчанию способ не выбран.
- Доступны две крупные radio-карточки: `Самовывоз` и `Доставка`.
- Самовывоз показывает актуальный процент скидки из CMS сразу, до выбора
  способа получения, и сохраняет подпись после выбора.
- Курьер показывает условия доставки из CMS.
- Выбор сохраняется в черновике текущей вкладки.

### Шаг 2. Данные

После выбора способа показываются:

- обязательное `ФИО` без строгой проверки количества слов;
- обязательный телефон с существующей нормализацией и проверкой;
- необязательный email с существующей проверкой формата;
- необязательный комментарий.

Для самовывоза форма показывает адрес из CMS без редактирования. Для курьера
показывается обязательное единое поле адреса с нативным
`autocomplete="street-address"` и placeholder
`Город, улица, дом, квартира, подъезд`. Внешний сервис подсказок не подключается.

Существующие обязательные согласия сохраняются.

### Шаг 3. Сумма и подтверждение

- Для курьера показывается стандартная сумма товаров; доставка в неё не входит.
- Для самовывоза стандартная сумма показывается зачёркнутой, рядом показывается
  сумма со скидкой.
- Сумма со скидкой округляется до ближайшего целого рубля.
- Для курьера используется дисклеймер из ТЗ о подтверждении наличия, расчёте
  доставки и согласовании оплаты.
- Для самовывоза используется вариант о подтверждении наличия, адреса, времени
  получения и согласовании оплаты.
- Кнопка называется `Подтвердить заказ`.
- После успеха показываются заголовок `Спасибо, заказ принят`, номер заказа и
  сообщение о последующей связи менеджера.

## 4. Immutable snapshot заказа

Сервер не доверяет клиентским ценам и коммерческим настройкам. Новый заказ
сохраняет:

- `deliveryMethod`: `pickup` или `courier`;
- адрес получения: снимок адреса самовывоза из CMS либо введённый адрес курьера;
- `pickupDiscountPercent`: снимок процента для самовывоза либо `0` для курьера;
- `totalRubles`: стандартную сумму серверных товарных цен;
- `discountedTotalRubles`: рассчитанную сервером сумму после скидки.

Повтор запроса с тем же idempotency key возвращает тот же заказ и не пересчитывает
его по новым настройкам CMS.

## 5. Уведомления о заказе

- После первого успешного создания заказа CMS отправляет служебное письмо через
  настроенный email-провайдер на `orderNotificationEmail`.
- Если покупатель указал email, CMS независимо отправляет ему подтверждение
  заказа; отсутствие email не считается ошибкой.
- Повторный idempotent-запрос не создаёт повторных писем.
- Тема служебного письма: `Новый заказ №{номер} — Brega Tea`; тема клиентского:
  `Заказ №{номер} принят — Brega Tea`.
- Служебное письмо содержит способ получения, ФИО, телефон, необязательный email, адрес,
  необязательный комментарий, строки заказа, стандартную сумму, процент скидки
  и сумму со скидкой.
- Клиентское письмо содержит номер, способ и адрес получения, комментарий,
  строки заказа и итоговые суммы, но не дублирует служебные контакты.
- HTML и text-версии собираются из Handlebars-шаблонов; HTML использует
  email-safe табличную вёрстку и автоматически экранирует пользовательские данные.
- Для курьера процент равен `0`, обе суммы совпадают.
- Ошибка любой доставки не откатывает заказ, не блокирует второе письмо и не
  меняет успешный ответ покупателю; в лог попадают только аудитория,
  техническая ошибка и номер заказа, без PII.
- Email-провайдер настраивается только переменными окружения; секреты не хранятся в CMS.

## 6. Strapi Admin

Карточка заказа показывает:

- способ получения;
- соответствующую подпись адреса;
- процент скидки;
- стандартную сумму;
- сумму со скидкой.

Обе суммы берутся из immutable snapshot, а не пересчитываются при чтении.
Заказы, созданные до появления новых snapshot-полей, остаются читаемыми:
считаются курьерскими без скидки, а сумма к оплате равна сохранённой стандартной
сумме.

## 7. Acceptance criteria

1. Без выбранного способа форма не показывает поля шага 2 и не отправляется.
2. Самовывоз не принимает адрес от клиента, сохраняет адрес и скидку из CMS и
   показывает рассчитанную сумму.
3. Курьер требует адрес, сохраняет скидку `0`, а обе суммы заказа совпадают.
4. Необязательный email можно оставить пустым; некорректный заполненный email
   отклоняется.
5. Повторный idempotent-запрос создаёт один заказ, один раз списывает stock и
   запускает не более одного уведомления.
6. Недоступность email-провайдера не меняет успешный результат уже сохранённого заказа.
7. Admin DTO и карточка содержат способ, адрес и обе суммы без технических полей.
8. Публичные тексты и SEO используют `Brega Tea`, текстовый логотип виден при
   пустом media-поле.
9. Unit, integration, keyboard, axe и затронутые visual tests проходят.
10. Visual regression покрывает на desktop и mobile как начальный выбор способа,
    так и выбранный самовывоз с адресом и двумя суммами.
11. Количество одной позиции ограничивается меньшим из актуального остатка и
    `maxItemQuantity`; CMS повторно проверяет этот лимит при создании заказа,
    поэтому его нельзя обойти прямым HTTP-запросом.
