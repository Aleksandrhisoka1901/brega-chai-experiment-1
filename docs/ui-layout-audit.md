# Brega Chai — UI и layout audit

Статус: завершён. Все замечания приняты; проверка финального production-контента
остаётся частью release hardening, а не этого remediation-аудита.

Этот документ фиксирует визуальные замечания этапа `UI и layout remediation`.
Этап завершается после закрытия всех `blocking`-замечаний, согласованной обработки
`polish` и итоговой ручной приёмки.

## Источники истины

При расхождениях действует следующий приоритет:

1. решение, принятое во время текущей визуальной приёмки;
2. `design-reference.html`;
3. `design-spec.md`;
4. `component-showcase.html`;
5. текущая реализация.

Если принятое решение меняет общий компонент или design token, одновременно
обновляются реализация и showcase.

## Viewport

Обязательные размеры:

- desktop: `1440 × 1000`;
- tablet: `1024 × 1366`;
- mobile: `390 × 844`.

Дополнительно проверяются границы `768 px` и `1280 px` без обязательных visual
snapshots.

## Порядок работы

1. Собрать все замечания desktop-аудита: главная, каталог, товар, корзина,
   checkout.
2. Выделить повторяющиеся проблемы и исправить общую layout foundation.
3. Исправить локальные проблемы storefront и commerce UI.
4. Выполнить сквозной типографический проход без висячих коротких предлогов,
   союзов и частиц.
5. Повторить аудит и исправления для tablet, затем mobile.
6. Выполнить сквозную responsive-проверку и итоговую visual QA.

До завершения desktop-аудита исправления не начинаются, чтобы общие проблемы не
маскировались локальными обходами.

## Классификация

- `blocking` — нарушена сетка, иерархия, читаемость, responsive-поведение,
  доступность или соответствие reference;
- `polish` — локальная микрокоррекция без функционального влияния;
- `later` — требует нового контента, функции или расширения scope.

Все `blocking` должны быть закрыты и приняты. `Polish` закрывается в текущей
ветке, если изменение локальное; иначе перенос явно фиксируется. `Later` не
блокирует этап, но сохраняется с причиной.

Статусы замечаний: `open → in progress → review → accepted`. Для перенесённых
замечаний используется `later`.

## Visual regression

Обязательные стабильные состояния:

- главная;
- каталог;
- карточка товара;
- корзина с несколькими позициями;
- checkout с пустой формой;
- checkout с validation errors;
- success-state.

Snapshots создаются на трёх обязательных viewport с детерминированными fixtures.
Для стабильных layout-инвариантов используются component/E2E assertions.

## Итоговая приёмка

- нет горизонтального overflow и случайных скачков сетки;
- интерактивные элементы не перекрываются;
- общие правила реализованы в design system без локальных обходов;
- keyboard, axe и reduced-motion проверки затронутых сценариев зелёные;
- все `blocking` имеют статус `accepted`;
- ручная visual QA подтверждена.
